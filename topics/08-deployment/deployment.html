Deploying ML Models

A model that lives only in a notebook helps nobody. Deployment means putting a trained model where real users or systems can use it, reliably and safely, and then keeping it healthy over time. This lesson follows the whole journey: saving the model, serving it through an API, packaging it, releasing it safely, and watching it once it is live.

Practical≈ 100 min3 interactive demos

1. The big idea: from notebook to real life

The test kitchen and the restaurant. A chef perfects a recipe in a test kitchen: that is training a model. Serving it to a thousand diners every night is a different job. You need the same ingredients delivered in the same form every time (consistent inputs), staff who can cook it fast (servers), someone tasting dishes to check quality (monitoring), and a plan for when the supplier changes or tastes shift (retraining). A great recipe with no kitchen system fails; a good recipe with a good system succeeds. Deployment is building that system around the model.

Deployment is not one step but a cycle:

2. How will predictions be used? Deployment patterns

The first design decision is when the prediction is needed.

A useful measurement. Timing a logistic-regression pipeline in scikit-learn 1.9.0 on my machine: predicting one row took about 0.42 milliseconds, but predicting 4,500 rows in a single call took about 0.73 milliseconds in total. Models are vectorised: handing them many rows at once is enormously more efficient per row, which is why batch jobs are cheap and why online services sometimes group several requests together. And a complete request through a web framework (below) took about 6.7 ms: for small models the surrounding service, not the model, is usually the slow part.

3. Step 1: save the model properly

Save the whole pipeline, not just the model

The number-one deployment bug is training–serving skew: the data is prepared one way during training and slightly differently in production (a different scaling, a category encoded in another order, a missing value filled differently). The model then silently gets inputs it was not trained for. The cure, from the ML Workflow lesson: put every preprocessing step and the model into one scikit-learn Pipeline, and save that. The saved object then contains the fitted scaler's means, the encoder's categories and the model's weights together.

joblib and pickle

Python objects are saved with pickle; joblib is a version of the same idea tuned for objects with big NumPy arrays, which is why scikit-learn recommends it. Here is a real run (scikit-learn 1.9.0, joblib 1.5.3):

import joblib, json, sklearn
from sklearn.datasets import load_iris
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import train_test_split

data = load_iris()
X_train, X_test, y_train, y_test = train_test_split(data.data, data.target, stratify=data.target, random_state=42)
pipe = make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000)).fit(X_train, y_train)
print(pipe.score(X_test, y_test))                      # 0.9211

joblib.dump(pipe, "iris_model.joblib")                 # ~1.6 KB for this tiny model
loaded = joblib.load("iris_model.joblib")              # takes about 15 ms
print((loaded.predict(X_test) == pipe.predict(X_test)).all())      # True: identical predictions

# save the facts you will need later next to the model (versions, feature order, metrics)
json.dump({"sklearn": sklearn.__version__, "features": list(data.feature_names),
           "classes": list(data.target_names), "test_accuracy": 0.9211}, open("iris_model.json", "w"))

Model files can be big: a random forest of 300 trees on the same data was 562 KB, and 78 KB with joblib.dump(model, path, compress=3). Large models (thousands of deep trees, neural networks) reach hundreds of megabytes, which matters for start-up time and cost.

Security: never load a pickle from somebody you do not trust. Loading a pickle file can run arbitrary code hidden inside it, exactly as if you had run their program. Only load model files that you created or that come from a trusted, verified source. Safer formats exist: skops (a persistence format for scikit-learn models that lets you inspect what will be loaded), and ONNX (a standard, Python-free model format that runs in a fast runtime on servers, phones and browsers). Neural-network libraries have their own formats (Keras, PyTorch, XGBoost's JSON), and tools such as MLflow provide a model registry that keeps versions, metrics and files together. I list those without demonstrating them here.

Match the versions. A pickled model is tied to the library version that made it. Record the scikit-learn, Python and NumPy versions with the model (as in the JSON file above) and load it in the same environment. scikit-learn warns you if the version differs, and a different version may give different results or fail to load.

4. Step 2: serve it through an API

An API (application programming interface) lets one program ask another for something over the network. For ML the usual choice is a web API: your model sits behind a web address ("endpoint"); a client sends a request containing the input as JSON (a plain-text format of named values), and the service replies with the prediction, also as JSON. The two most popular Python tools are FastAPI and Flask. Here is a complete FastAPI service for the iris model, which I ran and tested with FastAPI's built-in test client (fastapi 0.141.1, pydantic 2.13.5):

# app.py
import joblib
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel, Field

app = FastAPI(title="Iris service")
model = joblib.load("iris_model.joblib")                 # load ONCE when the service starts, not on every request
CLASSES = ["setosa", "versicolor", "virginica"]

class Flower(BaseModel):                                 # the "schema": what a valid request looks like
    sepal_length: float = Field(gt=0, lt=20)
    sepal_width:  float = Field(gt=0, lt=20)
    petal_length: float = Field(gt=0, lt=20)
    petal_width:  float = Field(gt=0, lt=20)

@app.get("/health")
def health():
    return {"status": "ok", "model_version": "1.0"}

@app.post("/predict")
def predict(f: Flower):
    proba = model.predict_proba([[f.sepal_length, f.sepal_width, f.petal_length, f.petal_width]])[0]
    k = int(proba.argmax())
    return {"species": CLASSES[k], "probability": round(float(proba[k]), 4)}

@app.post("/predict_batch")
def predict_batch(items: list[Flower]):
    if len(items) > 1000:
        raise HTTPException(413, "too many rows")
    rows = [[i.sepal_length, i.sepal_width, i.petal_length, i.petal_width] for i in items]
    return {"species": [CLASSES[k] for k in model.predict(rows)]}

# run it:   uvicorn app:app --host 0.0.0.0 --port 8000
# FastAPI also generates interactive documentation at /docs (I listed the routes it generates; I did not open the page)

POST /predict_batch (two flowers)               -> 200 {"species": ["setosa", "virginica"]}

Three ideas are at work: load once (reading the model file for every request would be slow), validate every input (the schema rejects missing, mistyped or impossible values before the model ever sees them), and return a clear, structured answer. Follow one request through the whole service:

Try the last option, "valid but absurd". A flower with a 19 cm petal passes the validation (the limit is 20) and the model answers virginica with 100% probability, because it extrapolates its straight-line rules far beyond any flower it has seen (the scaled value is 8.6 standard deviations from the training average). Validation checks the shape of an input; it does not check whether the model can be trusted on it. Sensible safeguards: ranges taken from the training data, an "out-of-distribution" flag when values are far from what was seen, and a human or default fallback when the model is unsure.

5. Step 3: package it so it runs the same everywhere

"It works on my machine" is the classic deployment failure: the server has a different Python or library version. Two remedies:

  • Pin the environment: a requirements.txt listing exact versions (for example scikit-learn==1.9.0, fastapi==0.141.1, joblib==1.5.3), installed in a fresh virtual environment.
  • Use a container (Docker): a container bundles your code, the Python version and all libraries into one image that runs identically on your laptop, a colleague's, and a cloud server. A minimal recipe (a Dockerfile):
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py iris_model.joblib ./
EXPOSE 8000
CMD ["uvicorn", "app:app", "--host", "0.0.0.0", "--port", "8000"]

# build and run (I have not run Docker for this course, so treat this file as a standard template to test yourself):
#   docker build -t iris-service .
#   docker run -p 8000:8000 iris-service

Also add automated tests: a few requests with known answers (like the ones above) that must pass before any release, so a broken model or a changed library is caught early.

7. Step 5: release it without breaking things

Do not switch everyone to a new model at once. Introduce it in stages, and always keep the old version ready:

  • Shadow mode: the new model receives real requests and makes predictions, but nobody sees them; you compare them with the current model and with what really happened.
  • Canary release: send a small share (say 5%) of traffic to the new model and watch errors and business numbers before increasing.
  • A/B test: split users between old and new and measure a business outcome (clicks, savings) with a proper statistical comparison: remember the wobble of small samples from the Evaluation Metrics lesson.
  • Rollback: keep the previous model version and a tested way to switch back in minutes.
  • Versioning: every deployed model has a version number, linked to the code, the data and the metrics it was built with, so any prediction can be traced.

8. Step 6: monitor and improve

Unlike ordinary software, a model can be running perfectly (no errors) while its predictions quietly get worse, because the world changes. Things to watch:

WhatExamplesWhy
System healthresponse time, error rate, memory, requests per secondthe service itself must work
Data qualitymissing values, out-of-range numbers, new categories, wrong typesupstream systems change without warning
Data driftthe distribution of an input feature moves away from what the model was trained onthe model may be extrapolating; an early warning
Concept driftthe relationship between inputs and the outcome changes (customers behave differently, fraudsters adapt)even with the same inputs, the old rules are now wrong
Model performanceaccuracy, recall, error, once the true outcomes are knownthe real report card; often arrives with a delay (a loan default takes months)
Business impactrevenue, complaints, savingsthe reason the model exists

Measuring drift: the population stability index (PSI)

You usually cannot compute accuracy today, because the true labels are not yet known. What you can compute today is whether the inputs look like the training inputs. A popular score is the PSI: split a feature into bins, compare the share of data in each bin then (reference) and now (live), and add up (live share − reference share) × ln(live share ÷ reference share) over the bins.

By hand. Five bins of, say, customer age. Reference shares (training data): 10%, 20%, 40%, 20%, 10%. Live shares this week: 5%, 15%, 35%, 25%, 20%.

BinReferenceLive(live − ref) × ln(live ÷ ref)
10.100.05(−0.05) × ln 0.5 = 0.0347
20.200.15(−0.05) × ln 0.75 = 0.0144
30.400.35(−0.05) × ln 0.875 = 0.0067
40.200.25(+0.05) × ln 1.25 = 0.0112
50.100.20(+0.10) × ln 2 = 0.0693
PSI = total0.136

A common rule of thumb: PSI below 0.1 = stable; 0.1 to 0.25 = moderate change, watch closely; above 0.25 = significant change, investigate. Here 0.136 says "moderate": the population is getting older. (These thresholds are conventions, not laws.)

Another tool is a statistical test comparing the two samples, such as the Kolmogorov–Smirnov (KS) test, which reports the largest gap between the two cumulative distributions and a p-value. A caution from a run with 2,000 samples each (standard normal versus a shifted normal): a shift of 0.1 gave D = 0.061 and p = 0.001, a shift of 0.3 gave D = 0.144 (p ≈ 10−18), 0.6 gave D = 0.244. With large samples even tiny, harmless shifts become "statistically significant", so look at the size of the drift (D or PSI) and not only the p-value.

Improving: when to retrain

  • On a schedule (weekly, monthly) when the world changes steadily and you have new labelled data.
  • On a trigger (drift alarm, performance below a threshold).
  • Champion / challenger: train a new model, compare it with the current one on recent data (and in shadow mode), and only replace the champion if the challenger is clearly better.
  • Beware feedback loops: if the model's decisions change the data it learns from (it only shows users what it predicts they like, then trains on their clicks), it can reinforce its own biases. Keep some exploration or random holdout.

9. Safety, privacy and responsibility

  • Protect the service: authentication, rate limits, input size limits, no internal error details in responses.
  • Protect the data: log only what you need; remove or hash personal information; follow the privacy laws that apply to you.
  • Check fairness: measure performance on subgroups (see the Evaluation Metrics lesson); an overall average can hide harm to a group.
  • Be transparent: document what the model is for and not for (a "model card"), its known weaknesses, and its training data.
  • Keep a human in the loop for high-stakes or low-confidence decisions, and give people a way to contest a decision.

Streaming services score huge catalogues in batch overnight and re-rank a short list in real time when you open the app.

📱 On your phone

🏭 Predictive maintenance

Sensor data streams to a model that flags machines likely to fail; alerts go to engineers, who can override it.

🏥 Clinical tools

Decision-support models run behind hospital systems with strict validation, audit logs and a clinician always in charge.

📊 Analyst dashboards

A small interactive app (built with tools like Streamlit, next lesson) lets a business team explore predictions without writing code.

Key takeaways

  • Deployment is a cycle: package → serve → release safely → monitor → retrain. The model is only one piece.
  • Choose the pattern from when the answer is needed: batch, real-time API, streaming, edge, or an interactive app. Models are far faster per row on batches (0.42 ms for one row vs 0.73 ms for 4,500 in my test).
  • Save the whole pipeline (preprocessing + model) with joblib, record versions, and never load untrusted pickles; consider skops or ONNX.
  • Serve behind an API (FastAPI or Flask): load the model once, validate every input, return structured answers and clear error codes. Validation does not stop a model being confidently wrong far from its training data: add range and out-of-distribution checks.
  • Package with pinned requirements or a container; release with shadow, canary or A/B stages and keep a rollback.
  • Monitor health, data quality, drift (for example PSI: 0.136 in our example = moderate), performance when labels arrive, and business impact; retrain on a schedule or trigger, with a champion/challenger comparison.
  • Take security, privacy, fairness and human oversight seriously from the start.
