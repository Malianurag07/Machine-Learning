Deployment using Streamlit

Streamlit turns an ordinary Python script into an interactive web app, with no HTML, CSS or JavaScript to write. For machine learning it is the fastest way to let a person try a model: move some sliders, press a button, see the prediction. This lesson explains the one idea that makes Streamlit different (the script re-runs from the top on every click), then builds a complete prediction app around the saved iris model from the previous lesson.

Practical≈ 90 min4 interactive demos

1. The big idea: a script that re-runs

The whiteboard that is wiped clean. Imagine a teacher who, every time a student changes one number on the board, wipes the whole board and redoes the entire worked example from line 1 with the new number. It is slow in theory but wonderfully simple: the teacher never has to think about "what changed?", the board always shows a picture that matches the current numbers. Streamlit works this way. Whenever you touch a widget, Streamlit runs your Python file again from the first line to the last and redraws the page. Your code stays a plain top-to-bottom script.

That single rule explains almost everything else in this lesson:

  • A normal variable is forgotten after each run (the script starts over), so you need session state to remember things.
  • Expensive work (loading a model, reading a big file) would be repeated on every click, so you need caching.
  • A widget is not an event handler you register: st.slider(...) is simply a function that returns the current value of the slider each time the script runs.

2. The smallest app

Install Streamlit, save a file, run it. I ran everything in this lesson with Streamlit 1.64.0, scikit-learn 1.9.0, joblib 1.5.3 and pandas 3.0.6. I tested the code headlessly with Streamlit's own test tool (streamlit.testing.v1.AppTest), which runs the script and lets you "click" widgets from Python. I did not open a browser on the real Streamlit server, so how the pages look in the browser is described from the documentation, not from my own screen.

# hello.py
import streamlit as st

n = st.slider("Pick a number", 0, 10, 3)      # returns the slider's current value
st.write("Its square is", n * n)

# terminal:   pip install streamlit
#             streamlit run hello.py          # opens http://localhost:8501

Move the slider and the text updates: the script just ran again with the new value of n. There is no callback and no page template.

Output is just as direct: st.write (shows almost anything), st.metric (a big number with a change), st.dataframe (a table), st.bar_chart / st.line_chart (quick charts, or pass a Matplotlib figure to st.pyplot), and the message boxes st.success, st.warning, st.error.

The button surprise. st.button is True for exactly one run. In my test app, I pressed Predict and the result appeared; I then moved a slider (a new run, in which the button is False again) and the result disappeared (0 metrics on the page). If that is not what you want, store the result in st.session_state (section 5) or use a form (section 6).

4. Caching: do not repeat expensive work

Because the whole script re-runs on every touch, a line such as joblib.load("model.joblib") at the top would reload the model on every slider move. Streamlit has two decorators for this. The first time the function runs with certain inputs, the result is stored; the next time it is called with the same inputs, Streamlit returns the stored result instead of running the function.

DecoratorUse it forWhat you get back
@st.cache_datadata: a loaded CSV, a query result, a computed tablea copy of the stored value each time (safe to change)
@st.cache_resourcethings you do not copy: a trained model, a database connectionthe same shared object every time, for all users

A real measurement (Streamlit 1.64.0, a function that sleeps one second, called with the same input): the first run took 1.00 s and the second 0.00 s. Streamlit's own debug log printed "Memory cache MISS" on the first run and "Memory cache HIT" on the second. Try the idea:

Two practical notes. The cache key is built from the function's arguments (and its code), so a different argument is a miss. And @st.cache_data(ttl=3600) makes stored results expire after an hour, useful when the underlying data changes.

5. Session state: remembering between runs

Each browser tab has its own st.session_state, a dictionary that survives reruns. Everything else (ordinary variables) starts again. I ran this tiny app and clicked "add" three times:

import streamlit as st
count = 0                                   # a plain variable: recreated as 0 on every run
if "n" not in st.session_state:             # create the remembered value only once
    st.session_state.n = 0
if st.button("add"):
    count += 1
    st.session_state.n += 1
st.write("plain", count, "state", st.session_state.n)

Real output after each click: plain 1 state 1, then plain 1 state 2, then plain 1 state 3; and on a run with no click, plain 0 state 3. The plain variable is always reset; session state keeps its value.

Callbacks. A widget can call a function before the rerun starts: st.button("bump", on_click=bump). This is the tidy way to update state. (In my test, clicking a button wired this way changed the stored total from 0 to 1.) Give a widget a key="name" and its value is also available as st.session_state["name"].

Session state is per tab, not per server. Two people using the app have separate session states, but they share anything stored with @st.cache_resource. Do not keep one user's data in a cached object.

7. A complete prediction app

Now everything together. This app loads the saved iris_model.joblib (the pipeline from the previous lesson: a scaler and a logistic regression, test accuracy 0.9211), takes four measurements from the sidebar, predicts on demand, shows the probabilities, warns when an input is outside the range of the training data, and keeps a history. I ran it with AppTest.

# app.py
import joblib
import pandas as pd
import streamlit as st

st.set_page_config(page_title="Iris predictor", page_icon="🌸", layout="wide")

CLASSES = ["setosa", "versicolor", "virginica"]
FEATURES = ["sepal length (cm)", "sepal width (cm)", "petal length (cm)", "petal width (cm)"]


@st.cache_resource                       # load the model ONCE per server, share it between reruns and users
def load_model():
    return joblib.load("iris_model.joblib")


@st.cache_data                           # cache plain data: the same inputs return the stored answer
def load_reference():
    from sklearn.datasets import load_iris
    d = load_iris(as_frame=True)
    return d.frame.rename(columns=dict(zip(d.feature_names, FEATURES)))


model = load_model()

if "history" not in st.session_state:   # session_state survives reruns (one per browser tab)
    st.session_state.history = []

st.title("🌸 Iris species predictor")
st.write("Move the sliders in the sidebar, then press **Predict**.")

with st.sidebar:
    st.header("Flower measurements")
    sl = st.slider(FEATURES[0], 4.0, 8.0, 5.8, 0.1)
    sw = st.slider(FEATURES[1], 2.0, 4.5, 3.0, 0.1)
    pl = st.slider(FEATURES[2], 1.0, 7.0, 4.3, 0.1)
    pw = st.slider(FEATURES[3], 0.1, 2.5, 1.3, 0.1)
    go = st.button("Predict", type="primary")

if go:
    row = pd.DataFrame([[sl, sw, pl, pw]], columns=FEATURES)
    proba = model.predict_proba(row.values)[0]
    k = int(proba.argmax())
    st.session_state.history.append({"species": CLASSES[k], "probability": round(float(proba[k]), 3)})

    left, right = st.columns(2)
    left.metric("Predicted species", CLASSES[k], f"{proba[k]:.1%} confident")
    right.bar_chart(pd.Series(proba, index=CLASSES, name="probability"))

    ref = load_reference()
    lo, hi = ref[FEATURES].min(), ref[FEATURES].max()
    outside = [f for f, v in zip(FEATURES, [sl, sw, pl, pw]) if not lo[f] <= v <= hi[f]]
    if outside:
        st.warning("Outside the range of the training data: " + ", ".join(outside))

tab1, tab2 = st.tabs(["History", "Training data"])
with tab1:
    st.dataframe(pd.DataFrame(st.session_state.history))
with tab2:
    st.dataframe(load_reference().head(10))

What happened when I drove it with AppTest (set the sliders, click Predict, read the page):

first load                              -> no exceptions, 4 sliders, 1 button, 2 tabs
sliders 5.1, 3.5, 1.4, 0.2 + Predict    -> metric "setosa", "98.1% confident"
sliders 6.7, 3.0, 5.2, 2.3 + Predict    -> metric "virginica", "95.3% confident"     (history now has 2 rows)
sliders 8.0, 3.0, 7.0, 2.5 + Predict    -> "virginica", "99.8% confident" and the warning
                                           "Outside the range of the training data: sepal length (cm), petal length (cm)"
move one slider, no click               -> the result is gone (button is False on that run); history still has 3 rows

These are exactly the same probabilities as the FastAPI service gave in the previous lesson (98.1% and 95.3%), because both load the same saved pipeline. The third case repeats the lesson from the API: the model is 99.8% "confident" about a flower far outside anything it was trained on, so the app shows the warning. A friendly interface makes an over-confident model more convincing, so range checks matter here too.

8. Running it and sharing it

Run it locally

python -m venv .venv                     # optional but recommended: an isolated environment
pip install streamlit scikit-learn joblib pandas
streamlit run app.py                     # then open http://localhost:8501 (the default port)

Keep app.py and iris_model.joblib in the same folder, because the app loads the model with a relative path. When you save app.py, Streamlit offers to rerun the app with your new code.

Deploy it

These are the usual routes. I describe them from general knowledge of the platforms; I have not deployed this app to any of them, so check the current documentation before you rely on the details.

OptionHowGood for

A starting requirements.txt, with the versions I used (pin your own):

streamlit==1.64.0
scikit-learn==1.9.0
joblib==1.5.3
pandas==3.0.6

And a template Dockerfile (not run by me: treat it as a standard starting point to test yourself):

FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py iris_model.joblib ./
EXPOSE 8501
CMD ["streamlit", "run", "app.py", "--server.port=8501", "--server.address=0.0.0.0"]

Secrets. Never put passwords or API keys in the code. Streamlit reads them from a .streamlit/secrets.toml file (kept out of your repository) and exposes them as st.secrets["name"]; hosting platforms have a settings page for the same purpose.

9. Streamlit or FastAPI?

They solve different problems and often work together:

StreamlitFastAPI (previous lesson)
Who uses ita person at a browseranother program
Outputa web pageJSON
Effortvery low: one Python filea little more: schemas, endpoints
Scaleruns the script per user session; fine for small groupsbuilt to serve many automated requests
Best fordemos, internal tools, what-if explorersproduction systems, apps and back ends

A common pattern: the real product calls a FastAPI model service, while a Streamlit app (built quickly for analysts) calls the same service or loads the same saved pipeline.

10. Common pitfalls

PitfallWhy it happensFix
The model reloads on every click and the app feels slowloading is outside a cache; the script re-runs from the top@st.cache_resource on the loader
A variable "forgets" its valueplain variables reset every run (demo above)st.session_state
The result vanishes when a slider movesst.button is True for one run onlystore the result in session state, or use a form
Training the model inside the apptraining re-runs on every interaction and takes minutestrain offline, save the pipeline, only load it in the app
Wrong feature order or scalingthe app builds inputs differently from trainingsave the whole Pipeline, pass a DataFrame with the training column names, test with known rows
File not found on the serverrelative paths differ from your laptopkeep the model in the repository and build paths from __file__ (pathlib.Path(__file__).parent)
One user's data leaks to anotheruser data stored in a cache_resource object (shared by everyone)keep per-user data in session state
Overconfident answers on odd inputsthe model extrapolates (99.8% in my test)range checks and warnings, as in the app
Unknown picklesloading a model file can run codeonly load files you made or trust (see the previous lesson)
Wrong package versions onlinethe server installs whatever requirements.txt sayspin versions to match the environment that trained the model

Also remember the limits: Streamlit reruns a script per session, so it is not a substitute for a scalable, secured production service, and it does not give you login or permissions by itself.

Key takeaways

  • Streamlit turns a Python script into a web app. The whole script re-runs, top to bottom, on every interaction; a widget function just returns the current value.
  • Cache expensive work: @st.cache_resource for the model, @st.cache_data for data. (My test: 1.00 s first call, 0.00 s cached.)
  • Ordinary variables reset every run; st.session_state remembers (per browser tab). st.button is only True for one run.
  • Organise with the sidebar, columns, tabs and forms; show results with st.metric, st.dataframe, charts.
  • A good app loads a saved pipeline (never trains inside the app), passes inputs in the training order, and warns when inputs are outside the training range.
  • Run with streamlit run app.py; deploy through Community Cloud, Hugging Face Spaces or Docker, pin your requirements.txt, keep secrets out of the code.
  • Streamlit is for people (demos, internal tools); FastAPI is for programs (production services). They complement each other.

Show answers

1. It shows 1 after each click, including the fifth: every click starts a new run of the script, so x is reset to 0 and then increased once. Keep the counter in st.session_state to reach 5 (the demo above shows exactly this).

2. In a small function near the top of the script, decorated with @st.cache_resource, so the model is loaded once and shared, not on every rerun.

3. (a) Save the result in st.session_state when the button is pressed and display it from there; (b) put the sliders and button inside an st.form so the script only re-runs on submit; (c) compute the result without a button at all, so it updates on every slider move (fine when the model is fast).
